# 实验与评估

本文记录已有实验框架、检索代理实验结果及作业与提案要求对应的待执行评估设计。项目要求及完成情况见[项目目标与进度](project.md)，方法与分数定义见[检索 API](retrieval.md)；推荐接口见[基础生成](recommendation.md)和[证据生成](evidence_grounded_generation.md)。核对日期：2026-10-31。

## 仓库当前状态

仓库已实现 BM25、HNSW、四种混合检索策略（HRRF、HPRF、SemanticRRF、SD Cascade）、独立 FC-HNSW、查询生成、基础推荐生成及带原文证据的下游创新。

历史检索脚本曾对 40 条示例查询运行 BM25、HNSW、HRRF、FC-HRRF 四方法代理实验，输出保留于 `experiments/results/`。旧脚本及 FC-HRRF 混合实现已删除，历史实验使用 `collection_topic` 作为二值代理相关性，只能用于主题级比较，不属于正式人工相关性评估，也不提供生成质量结论。

上述已保存结果使用旧版双字段 FTS5 BM25，FC-HRRF 在 HRRF 固定候选上使用各分面排名百分位的最小值作为覆盖度。2026-10-31 起，标题、摘要独立计算 BM25 后加权相加；HPRF 替代旧 Facet Coverage 混合检索，沿用 HRRF 候选预算，将三处融合改为排名百分位加权。`sparse_semantic_weight`、`dense_semantic_weight`、`fusion_weight` 默认均为 `0.5`，尚未调参或评估。历史效果、延迟和覆盖权重选择不能作为 HPRF 的评估结论，本次保留历史结果和原始报告，未执行测试或实验。

当前没有 HPRF 专用检索实验脚本，也未迁移旧实验的自动调参流程。

独立 FC-HNSW 现为引擎和混合检索的默认 dense 组件，省略引擎 `method` 时使用
`FC_HNSW`。它与 `MULTI_QUERY_HNSW` 的搜索默认每分面候选深度均为
`ceil(limit * sqrt(m))`，其中 `m` 为去重后的分面数；单查询 `HNSW` 对应 `m=1`。
历史四方法实验使用当时的原多查询检索器及候选预算，不能代表当前预算下的效果或延迟。
独立 FC-HNSW 及新默认混合候选尚未重新评估，已有报告不能
作为其效果或延迟结论。

`experiments/generation/` 已提供固定候选导出和配对生成框架，可保存基础与证据生成方法的输出、运行状态与耗时；尚未实现人工标注、一致率或生成质量指标汇总程序，也未提供正式五查询结果与耗时、人工标注集、人工相关性指标或生成质量结果。下文的人工标注与正式评估指标口径仍为待执行设计，不依据未纳入 Git 的本地实验材料作出效果结论。

2026-10-19 从 `data-preprocessing` 同步的[查询示例](../data/example_queries.json)包含 40 条中英文研究请求，覆盖十个收录主题，可用于试用及后续评估选题；尚无人工相关性标签或人工确定的目标论文集合，不能直接作为已有人工评估集。

2026-10-28 的代理实验按主题各取首条查询组成 10 条开发集，其余 30 条为测试集；内部候选深度为 50，保存 Top-20，报告 K=10。开发集从 `0.1`～`0.5` 选择 FC-HRRF 覆盖权重。完整数值、bootstrap 区间和限制以[检索代理实验报告](../experiments/results/report.md)为准；正式报告不得把这些代理标签描述为人工相关性判断。

## 人工评估集设计（待执行）

按提案，准备约 100 条不重复研究需求，对各方法候选取并集并按 `(query_id, doc_id)` 去重，再人工判断至少 1,000 个 query–paper 对。候选池应覆盖不同主题及具体约束，不能靠重复结果凑足标注量。用于改进方法的开发查询与用于最终报告的留出查询应分开，记录各自用途，避免在同一批标签上调参和报告结果。

相关性采用提案的三级标注：`0` 不相关、`1` 部分相关、`2` 高度相关。至少两名标注者独立阅读同一请求及论文标题、摘要；标注时隐藏检索方法、分数和排名。先记录原始标签并计算一致率，再对分歧进行讨论或仲裁，保存最终标签及说明。课程要求一致率至少 80%；建议另报告 Cohen's kappa 以补充反映偶然一致的影响。

以下是建议用于正式评估的 JSONL 记录约定。现有生成实验脚本的实际输出字段见[生成对比实验](../experiments/generation/README.md)；完整标注、仲裁和指标汇总流程尚未实现：

| 材料 | 建议字段 |
| --- | --- |
| 查询 | `query_id`、`request`、`split`、`topic`、`constraints` |
| 固定检索输入 | `query_id`、`terms`、`recall_queries`、`query`、生成模型与提示词版本 |
| 各方法运行结果 | `run_id`、`query_id`、`method`、`rank`、`doc_id`、`score`、`score_type` |
| 原始标注 | `query_id`、`doc_id`、`annotator_id`、`relevance`、`note` |
| 仲裁后标签 | `query_id`、`doc_id`、`relevance`、`adjudication_note` |
| 推荐生成与证据 | `run_id`、`query_id`、推荐论文 ID、理由、引用摘要及支持性判断 |

检索相关性标签用于评估候选排序，不能单独替代对推荐理由的人工或模型辅助评估。生成完成后，仍需检查理由是否被摘要支持、推荐是否满足需求以及引用是否正确。

## 检索指标与比较（待执行）

正式报告以 Top-10 目标为主，可同时报告 K=5、10、20。二值指标需事先固定相关阈值（例如标签 ≥1）；NDCG 使用完整的 0/1/2 分级标签，并明确增益定义。对同一批查询按查询平均，说明无相关论文或标签不足时的处理。

| 指标 | 报告口径 |
| --- | --- |
| Precision@K | 前 K 个位置中相关论文数除以 K；不足 K 篇时需明确缺失位置处理 |
| Recall@K | 前 K 篇相关论文数除以该查询候选池内已标注相关论文数；这是候选池召回率，不是全库或整个 arXiv 召回率 |
| MRR | 第一篇达到相关阈值的论文排名倒数；若只评估前 K 篇，应写为 MRR@K |
| NDCG@K | 用分级相关性衡量排序质量，理想排序基于共同标注候选池 |

未标注候选不应悄悄当作不相关；加入新方法或扩大返回深度后，应补齐所需标注或明确未判定比例及局限。候选池之外的相关论文未知，因此不能宣称已测得全库 Recall。

现有检索方法可直接纳入比较，但需先冻结一项 hybrid 作为基线，再说明创新引入了什么变化。多查询、整合查询重排、分层 RRF、语义权重和级联候选选择均有实现，尚不能把其组合收益归因于其中任一项。若要做严格消融，应固定语料、模型、检索输入、K 和候选预算；不同方法当前的候选预算不同，需记录并分析这一影响。

还需区分两种实验：固定 `terms/recall_queries/query` 比较检索与排序，以及包含实时 LLM 查询生成的端到端比较。`SearchEngine` 的 HNSW 方法生成一条整合查询并执行单查询近似召回；MULTI_QUERY_HNSW 方法另外生成分路查询，再由 `MultiQueryHNSWRetriever.search` 合并并重排。前者调用一次 LLM，后者在检索前调用两次，空召回也不减少调用次数。比较时应同时记录查询生成成本和每分路候选预算。

## 推荐生成与性能评估（待执行）

固定检索候选及顺序、研究需求、推荐数量上限、生成模型、API 配置、thinking 强度及并发上限后，比较基础 `RecommendationGenerator` 与 `EvidenceGroundedRecommendationGenerator`。两种方法共用逐篇判断与集中筛选排序流程、统一结果和引用格式，变化仅为逐篇判断提示词，其余条件应保持一致。最终数量为 `min(limit, 初筛推荐数)`，需同时报告实际返回数量。若引入多项创新，分别记录单项和组合结果。推荐任务需说明采用哪些任务质量指标及其理由；没有参考推荐理由时，不应虚构参考答案并报告摘要指标。

现有脚本先通过 `prepare_candidates.py` 检索并保存候选，再通过 `run_comparison.py` 读取同一文件运行两种生成器。默认输出在被 Git 忽略的 `experiment/generation/`，使用方式与字段见[生成对比实验](../experiments/generation/README.md)。两种生成器均对全部初筛理由中的 `[[cite]]原文[[/cite]]` 执行精确原文校验，包含不推荐项；第二阶段仅处理推荐项，最终理由复用第一阶段结果。脚本保存成功输出及捕获到的 `RuntimeError`，不自动计算证据通过率或人工质量指标，API 和结构化解析异常仍可能中断运行。生成器先截取前 30 个候选再去重，超过此数量的导出候选不参与生成。本轮两阶段流程尚未执行运行验证。

生成评估至少覆盖理由的 faithfulness（每项主张是否有摘要依据）、answer relevance（是否回答研究需求）、context relevance/precision（上下文是否相关）、引用对应关系，以及证据生成方法中 evidence 对 reason 的语义支持性。精确字符串匹配不能替代这些判断。可结合人工标注与 RAGAS 等工具，但质量评估实现和结果目前均未提供；若使用模型裁判，需保存裁判模型、版本和判定规则。

五查询的速度测量仍待完成。正式记录应包含运行时间、代码版本、依赖、数据／索引标识、向量模型 revision 与指令、LLM 配置、硬件、K、候选规模和缓存条件。分别统计模型加载等冷启动开销与复用组件后的查询耗时，区分 LLM 查询生成、查询编码、召回／重排和下游生成；报告重复次数、平均值或中位数及适当分位数，并保存每个查询的原始测量。

吞吐、成本与可扩展性需基于明确的并发、缓存和语料规模实验；本地模型的预计算时间不能从总成本中无说明地剔除，LLM token 与费用也不能仅按调用次数推断。现有代理实验的延迟仅覆盖检索阶段，不包含 LLM 调用和查询编码；仓库尚未提供端到端吞吐、成本与可扩展性结论。
